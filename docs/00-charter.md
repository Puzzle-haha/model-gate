# ModelGate —— 项目章程

> 多模型 LLM 调用网关：可靠、可计量、可用数据选型。
>
> 本文件是接下来 4 个月的总纲。**每次动手前先看它，防止范围蔓延。**

---

## 1. 一句话定位

**让上层应用只调一个接口，底下自动完成供应商路由、密钥轮询、限流、熔断、降级、缓存、成本核算，并用实测数据回答「这个场景该用哪个模型最划算」。**

演示姿势（这是面试时的杀手锏）：

```bash
# 任何 OpenAI 兼容的客户端，把 base_url 指过来就能用
curl http://127.0.0.1:8081/v1/chat/completions \
  -H "Authorization: Bearer mg-demo-key" \
  -d '{"model":"auto","messages":[{"role":"user","content":"你好"}]}'
```

注意 `model: "auto"` —— 由网关根据成本和质量策略决定用哪家。这一句话就是整个项目的价值主张。

## 2. 为什么这个项目对你有价值

| 面试维度 | 这个项目能提供的证据 |
|---|---|
| 后端基本功 | 限流、熔断、重试、幂等、并发、缓存、连接池、事务 |
| 数据与存储 | MySQL 表设计、聚合查询、索引、Redis 原子操作与 Lua |
| 稳定性工程 | 实测的故障转移成功率、P95/P99 延迟、熔断恢复时间 |
| 成本意识 | 缓存命中率、分类模型选型带来的成本降幅 |
| 工程素养 | 配置化、可观测性、压测报告、评测集与回归 |
| 技术判断力 | 为什么不用现成网关、为什么这么分层、限流算法怎么选 |

**最关键的一点：它天然产出数字。** 「我把 P95 从 3200ms 降到 480ms」比「我实现了熔断器」有说服力得多。

## 3. 系统边界

### 做

- ✅ OpenAI 兼容的统一入口（`/v1/chat/completions`）
- ✅ 多供应商适配（DeepSeek 官方 + 任意 OpenAI 兼容中转 + 内置 mock）
- ✅ 路由与故障转移、多密钥轮询与密钥级熔断
- ✅ Redis 令牌桶限流与配额
- ✅ 响应缓存（精确匹配）
- ✅ 调用日志、token 与成本核算
- ✅ 可观测性（指标 + Dashboard）
- ✅ 评测集与模型质量回归
- ✅ 压测报告、部署上线

### 明确不做（保护你的时间）

- ❌ 分布式多机集群、K8s、服务网格
  —— 单机讲清楚原理就够。**面试官问的是原理，不是你的机器数量。**
- ❌ 完整用户体系、支付计费
  —— 用 API key 区分租户就够了
- ❌ 模型微调 / 训练
- ❌ 语义缓存（向量相似度匹配）
  —— 时间够再说，优先级最低
- ❌ 自己写前端框架
  —— Dashboard 用原生 JS + ECharts CDN，不引入 npm 构建链

> **项目最大的敌人不是难度，是做不完。**
> 一个完整跑通、有实测数据、能讲透的单体服务，远胜一个烂尾的分布式系统。

## 5. 里程碑

每个里程碑都必须**可验收 + 有数字**。没有数字的里程碑不算完成。

### M1 · 最小可用网关（约 2 周）

**做什么**
- `/v1/chat/completions` 入口，请求/响应结构与 OpenAI 对齐
- `Provider` 抽象 + `MockProvider`（复用 Phase 0 的故障注入）
- 一个真实 Provider（DeepSeek 官方）
- 调用日志落库（供应商、模型、耗时、token、是否降级）

**验收标准**
- 用 `curl` 或任意 OpenAI SDK 指向本服务能拿到正常回复
- 数据库里能查到每一次调用的记录
- `MockProvider` 注入超时/错误时，接口仍返回 200 + 降级内容

**产出数字**：正常路径延迟基线

---

### M2 · 多供应商路由与故障转移（约 3 周）

**做什么**
- Provider 配置化（名称、base_url、密钥、模型映射、单价）
- 按 `model` 名路由；`auto` 时按策略选
- 健康探测 + 自动故障转移
- 多密钥池：轮询、按密钥统计、密钥级熔断

**验收标准**
- 配 3 个 Provider，把其中一个的地址改成不可达 → **请求自动切到下一个，成功率不掉**
- 单密钥配额打满 → 自动换下一个密钥

**产出数字**：单点故障时成功率、故障转移平均耗时

---

### M3 · 限流与配额（约 2 周）

**做什么**
- Redis 令牌桶（Lua 脚本保证「读-判断-扣减」原子性）
- 按 API key / 租户维度限流
- 配额（按天/月），耗尽返回 429 + `Retry-After`
- 与熔断配合：限流拒绝不算 Provider 失败

**验收标准**
- 并发压测下实测 QPS 与设定阈值误差 < 5%
- 超过配额后立即 429，且**不产生任何上游调用**（省成本）

**产出数字**：限流精度、被拦截的无效调用数

> ⚠️ 这里是面试重灾区：**为什么用 Lua？不用会怎样？** 你必须能讲出「check-then-act」的竞态。

---

### M4 · 响应缓存与成本核算（约 2 周）

**做什么**
- 精确缓存：`hash(model + messages + 参数)` → 响应，带 TTL
- 成本核算：按 token 单价累计，按天/模型/租户聚合
- 缓存命中不计上游成本（这是省钱的核心证据）

**验收标准**
- 重复请求命中缓存，**延迟下降一个数量级**
- 成本报表与实际 token 用量对得上

**产出数字**：缓存命中率、延迟降幅、成本降幅

---

### M5 · 可观测性与 Dashboard（约 3 周）

**做什么**
- 指标：QPS、P50/P95/P99、错误率、降级率、token 用量、成本
- Dashboard 页面：实时曲线、供应商健康状态、熔断器状态、成本排行
- 前端：原生 JS + ECharts CDN，不引入构建链

**验收标准**
- 页面实时反映压测期间的指标变化
- 熔断触发时页面能看到状态变化

**产出数字**：Dashboard 截图（简历和面试都能用）

---

### M6 · 评测集与模型质量回归（约 2 周）

**这是整个项目最有差异化的一段。**

**做什么**
- 评测集：一批固定任务 + 期望结果（分类、抽取、摘要等）
- 跑评测：同一批任务在不同模型上跑，记录得分/耗时/成本
- 生成对比报告：**哪个模型在什么任务上最划算**

**验收标准**
- 一份可复现的评测报告
- 一个基于数据的路由策略：「分类任务走便宜模型，复杂推理走贵模型」

**产出数字**：各模型准确率/成本对比表

> 这一段直接回答「Agent 工程最难的是什么」—— 不是调 API，是**把不确定的系统变得可评测、可回归**。

---

### M7 · 压测、部署与简历（约 2 周）

**做什么**
- 压测报告（并发梯度、瓶颈定位）
- 部署上线（Linux 云服务器 + systemd；本机无 Docker）
- README、架构图、简历文案、面试追问自测

**验收标准**
- 一个可以访问的线上地址
- 简历上那三行 bullet 每条都有数字支撑

## 6. 技术栈与选型理由

| 组件 | 选型 | 为什么 |
|---|---|---|
| 语言 | Java 21 | 岗位量最大，环境已就绪 |
| 框架 | Spring Boot 3.5.16 | 教程/八股覆盖率高（4.x 太新，卡住搜不到答案） |
| 数据库 | MySQL 8.0.42 | 调用日志、成本、评测结果 |
| 缓存/限流 | Redis 5.0.14 | 令牌桶、响应缓存 |
| 迁移 | Flyway | 表结构版本化，别用 `ddl-auto` |
| 指标 | Actuator + Micrometer | 标准方案，面试认可 |
| 前端 | 原生 JS + ECharts CDN | 不引入 npm 构建链，把时间留给后端 |
| 构建 | Maven Wrapper | 别人 clone 下来不用装 Maven |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| **做不完**（最大风险） | 每个里程碑独立可交付；M5 结束就已经是一个能写进简历的完整项目，M6/M7 是加分项 |
| API 费用失控 | 默认走 `MockProvider`；真实调用只在验证时少量进行；缓存 + 配额双重限制 |
| 范围蔓延 | 有「明确不做」清单；新想法先记到 `docs/backlog.md`，不进当前里程碑 |
| 卡住超过 2 天 | 立刻降级方案，不硬磕。记录下来，面试时「我为什么放弃方案 X」也是加分项 |
| 只会做不会讲 | 每个里程碑结束写 3 句话：做了什么、为什么这么做、数据是多少 |
