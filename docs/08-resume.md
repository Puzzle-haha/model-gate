## 二、逐条拆解：这条想证明什么，会被追问什么

简历上的每一行都应该经得起"为什么"和"怎么做的"两轮追问。
下面是每条 bullet 的**设计意图**和**预设追问**。

### Bullet 1：可靠性工程

**想证明的**：你不是只会写 CRUD，你理解"依赖会挂"这件事，并且知道怎么把故障隔离住。

**关键技术细节（必须能讲）**：

| 细节 | 一句话解释 |
|---|---|
| 超时后 `cancel(true)` | 只"不再等待"不取消，工作线程会继续占用，池子被永久占死 → 服务"静默死亡"（不抛异常、不记日志、健康检查仍为 UP） |
| 401 只重试 1 次 | 密钥错了重试一万次结果一样，只会放大负载。线上的"重试风暴"就是这么来的 |
| 熔断粒度 = `(供应商, 模型)` | 限流、模型下线往往是单个模型的故障，按供应商熔断会让一个模型拖垮全家的服务 |
| 线程池粒度 = `供应商` | 目的是限制"对某个上游的总并发"；按模型建池会让 10 个模型 × 4 线程 = 40 并发打到同一家 |

**预设追问**：
- "熔断和降级什么区别？" → 熔断是**不再尝试**（快速失败），降级是**返回兜底内容**。两者配合：熔断打开时直接走降级，省掉重试开销。
- "你怎么知道熔断阈值设 5 是对的？" → 老实说：初始值是根据"能容忍几次瞬时抖动"拍的，真正的依据要靠 M5 的指标长期观察调整。**能承认这一点比编一个理由好。**
- "如果下游不响应中断怎么办？" → `cancel(true)` 就失效了。这时唯一可靠的防线是线程池隔离——让它死也只死自己那一块。这个追问很常见，要能答。

### Bullet 2：限流与缓存

**想证明的**：你知道并发问题出在哪，并且知道怎么用工具解决它。

**关键技术细节**：

| 细节 | 一句话解释 |
|---|---|
| 为什么必须用 Lua | 令牌桶是"读-判断-扣减"三步。分成三条命令时，并发请求会读到同一个值然后都放行 —— 经典 **check-then-act 竞态** |
| 这个 bug 为什么难发现 | 低并发下几乎不出现，只在并发或多实例部署时暴露。所以验证方式是**并发打 40 个请求看放行数是否严格等于 20**，而不是"发几个请求看有没有 429" |
| 缓存为什么只缓存 `temperature=0` | LLM 在温度 >0 时同样输入产生不同输出，这是特性。缓存它 → 用户要 10 个不同标题却每次拿到同一个，**功能"能用"但语义是错的** |
| 单飞防击穿 | 热点键过期的瞬间 N 个并发一起去打上游，缓存反而制造尖峰 |

**预设追问**：
- "为什么用令牌桶不用固定窗口？" → 固定窗口在切换瞬间会被击穿：第 59 秒打满 300 次，第 61 秒又打满 300 次，两秒内实际放行 600 次。令牌桶按时间连续补充，没有边界问题。
- "Redis 挂了怎么办？" → **fail-open**：放行并记警告。理由：限流是保护措施，不该成为单点故障源。如果更怕上游被打挂（按量付费场景），就该改成 fail-closed —— **这是业务判断不是技术判断**。已实测：停掉 Redis 服务仍返回 200。
- "缓存键怎么设计的？" → 长度前缀序列化后 SHA-256。**这里有个真坑**：用分隔符拼接时，`[("user","a\nmsg:assistant:b")]` 和 `[("user","a"),("assistant","b")]` 会拼出同一个键，导致 B 拿到 A 的答案。长度前缀从语法上消除歧义。

### Bullet 3：成本与评测

**想证明的**：**这一条是你和其他候选人最大的差别。** 大多数人做 LLM 项目到"能跑通"就停了；你做到了"能回答该用哪个模型"。

**关键技术细节**：

| 细节 | 一句话解释 |
|---|---|
| 为什么金额用整数微元 | 浮点无法精确表示十进制小数，单价 × token 数会产生无限小数，累加几百万次后报表和账单对不上。而且两个 10⁶ 正好抵消：`成本(微元) = tokens × 单价`，不用做除法 |
| 评测必须绕过缓存 | 否则第二次跑全是缓存命中，准确率变成假的 100%。**而且这个错误看起来像好事**，能骗过好几个迭代 |
| 为什么拆到"模型 × 任务类型" | 总分 58% 看不出问题；拆开才发现某模型情感分类只有 50%（等于抛硬币）而算术有 67%。路由决策需要这个粒度 |
| 打分器为什么要归一化 | `19` / `19。` / ` 19 ` 语义相同，直接比较会把后两个判错 —— 那你测的是"模型有没有按格式输出"而不是模型能力。但也不能过度归一化 |

**预设追问**：
- "每个正确答案成本怎么算的？" → 该模型总成本 ÷ 答对题数。单看准确率会永远选最贵的，单看成本会永远选最便宜的，只有两者结合才有决策价值。
- "这个评测集有什么局限？" → 只有 12 道客观题，覆盖不了主观任务（写作、总结）。而且题量太小，58% 和 67% 的差异可能不显著。**能指出自己评测的局限，比声称它很权威更能加分。**

## 三、不该写什么

| ❌ 不要写 | 原因 |
|---|---|
| "高并发分布式系统" | 这是单机服务。面试官一问"几台机器、怎么做的服务发现"就崩 |
| "支持千万级 QPS" | 实测 1776 req/s，而且瓶颈在上游。编数字是最容易被戳穿的 |
| "精通 Spring Boot" | 面试官会往深里问。写"熟悉"更安全 |
| "实现了一个 Agent" | 这个项目是网关，不是 Agent。**准确描述比蹭热词安全** |
| 没有数字的功能罗列 | "实现了限流、缓存、监控" —— 这种句子面试官会直接跳过 |

## 四、项目描述的顺序建议

简历上项目条目的顺序应该**按你最能讲透的顺序排，而不是按开发顺序**。

推荐顺序（和上面的 bullet 一致）：
1. **可靠性** —— 技术含量最高，最能体现工程素养
2. **限流与缓存** —— 有硬核的并发正确性故事
3. **成本与评测** —— 差异化最强，但需要一定的解释成本

如果面试官看起来对 AI 应用特别感兴趣，可以把第 3 条提前。

## 五、一句话总结（自我介绍时用）

> 我做的 ModelGate 是一个多模型调用网关。核心想法是：调用大模型这件事本身不难，
> 难的是**当它不稳定、要花钱、而且不同模型效果不一样的时候，你怎么让系统还能可控地跑**。
> 所以我在可靠性、成本和质量三个方面都做了量化 —— 上游挂了能自动切、调用花了多少钱
> 能精确到微元、以及用评测集回答"这类任务该用哪个模型最划算"。
