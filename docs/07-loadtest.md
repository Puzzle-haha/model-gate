# 压测报告

> 数据采集时间：2026-10-02 · 本机（Windows 11，单机，客户端与服务端同机）

---

## ⚠️ 先说清楚这份报告测的是什么、不是什么

**这一条比数字本身重要。** 一份不声明测量边界的压测报告是没有价值的，
因为它会被误读。

| 项目 | 说明 |
|---|---|
| ✅ **测的是** | 网关自身的处理开销：路由、缓存查找、限流判定、日志入队、序列化 |
| ❌ **不是** | 真实 LLM 上游的性能。上游是本地 Node 假服务（单线程） |
| ❌ **不是** | 多机分布式场景。本机单实例，客户端与服务端抢同一颗 CPU |
| ❌ **不是** | 生产容量规划。数据只用于横向对比（有缓存 vs 无缓存、并发 50 vs 100） |

**换句话说：这组数字的价值在于"相对差异"，不在于"绝对吞吐"。**
面试被问"你这个 1776 QPS 说明什么"，正确的回答是
"它说明缓存把吞吐提升了 2.7 倍"，而不是"我的网关能扛 1776 QPS"。

## 一个必须先解决的方法论问题

第一次压测得到了一组**荒谬的数据**：

| 测试 | P95 |
|---|---|
| A. 缓存命中路径（**不调上游**） | **415 ms** |
| B. 完整路径（**调上游**） | 47 ms |

不调上游反而慢 9 倍 —— 显然不对。

根因：**测试 A 跑在应用刚启动时，包含了 JIT 编译预热**。
JVM 在最初几百次请求里处于解释执行 + 热点编译阶段，延迟可能是稳态的十几倍。
而第一个跑的测试总是最惨的，于是得出"缓存路径比不走缓存还慢"这种结论。

修法：**加预热阶段，跑 800 次请求后清空统计再开始测量。**
`tools/loadtest.mjs` 因此增加了 `--warmup` 参数。

> 教训：**性能数字必须标注是否预热。** 没有预热说明的压测数据，
> 你无法判断它反映的是服务性能还是 JVM 启动过程。
> 这个道理同样适用于对比不同实现 —— 谁先跑谁吃亏。

## 测试结果（已预热 800 次请求）

### A. 缓存命中路径（不调用上游）

```
请求数 1000  并发 50
吞吐        1776 req/s
总耗时      563 ms
P50  23 ms   P95  61 ms   P99  96 ms   max 103 ms
全部 200，无 429，无网络错误
```

缓存统计：`hits=950, coalesced=49, misses=1, puts=1`
—— 1000 个请求里只有 **1 次**真正去加载，49 个被单飞合并等它，950 个直接命中。

### B. 完整路径（含上游调用，并发 50）

```
请求数 1000  并发 50
吞吐        662 req/s
总耗时      1511 ms
P50  17 ms   P95 281 ms   P99 786 ms   max 936 ms
全部 200
```

### C. 完整路径（含上游调用，并发 100）

```
请求数 1000  并发 100
吞吐        656 req/s
总耗时      1524 ms
P50  34 ms   P95 326 ms   P99 818 ms   max 935 ms
全部 200
```

## 结论

### 1. 缓存把吞吐提升 2.7 倍，P99 降低 8 倍

| | 吞吐 | P50 | P95 | P99 |
|---|---|---|---|---|
| 无缓存（B） | 662 req/s | 17 ms | 281 ms | 786 ms |
| 有缓存（A） | **1776 req/s** | 23 ms | **61 ms** | **96 ms** |

P50 基本没变（17 → 23 ms），因为**一半的请求本来就很快**。
真正的收益在长尾：P99 从 786 ms 降到 96 ms。

这又一次印证了 M5 那个结论 —— **只看平均值会漏掉全部收益**。

### 2. 并发从 50 提到 100，吞吐不变，说明瓶颈已在上游

```
并发 50  → 662 req/s
并发 100 → 656 req/s   （+0%）
```

吞吐不再增长而 P95 继续上升（281 → 326 ms），这是**瓶颈转移**的典型特征：
瓶颈不在网关，而在本地单线程的 Node 假上游。

**而且这恰好是网关该有的表现。** 网关的职责是保护上游不被压垮，
而不是自己成为新的瓶颈。如果并发翻倍吞吐也翻倍，说明压力全打到上游去了 ——
那才是设计失败。

### 3. 日志异步通道在 1776 req/s 下零丢失

```
submitted 3801 / written 3801 / dropped 0 / writeFailures 0
```

这验证了 M1 那个设计决策：**日志不能拖慢主链路，队列满了宁可丢也不阻塞请求**。
在当前压力下队列从未接近容量（10000），异步批量方案完全跟得上。

### 4. 资源占用

| 项 | 值 |
|---|---|
| 进程内存 | 439 MB |
| CPU 累计（全部测试） | 61.5 s |
| 线程数 | 173 |

线程数偏高（Tomcat 工作线程 + 每供应商 4 个上游线程 + JVM 内部线程）。
单机开发环境下无需优化，但这解释了为什么上游线程池要**按供应商隔离而不是按模型**
—— 按模型建池会让线程数随模型数量线性膨胀。

## 复现方式

```powershell
# 终端 1：假上游
node tools/fake-upstream.mjs

# 终端 2：应用（关闭限流以便测吞吐）
java -jar target/model-gate-0.1.0-SNAPSHOT.jar `
  --spring.config.additional-location=file:./tools/localtest.yml `
  --modelgate.ratelimit.enabled=false

# 终端 3：压测（务必加 --warmup）
node tools/loadtest.mjs --requests 1000 --concurrency 50 --warmup 800 `
  --api-key bench-a --model fake-fast --temperature 0 --identical --prompt "基准A"

node tools/loadtest.mjs --requests 1000 --concurrency 50 --warmup 800 `
  --api-key bench-b --model fake-fast --temperature 0.7 --prompt "基准B"
```

> 注意两次测试用了**不同的 api-key**，因为缓存键包含租户（`include-tenant: true`），
> 同 key 会让第二次测试命中第一次的缓存，测不出完整路径的真实开销。
